# 3.3.5 Help

**Level:** AAA | **Standard:** WCAG 2.2
**Spec:** <https://www.w3.org/TR/WCAG22/#help>

## Why manual

Whether context-sensitive help is "available" for form inputs requires understanding the input's purpose and verifying that help content exists and is reachable. Static analysis can detect form elements but cannot determine whether the help available is contextually adequate or present at all.

## What to verify

> "Context-sensitive help is available."

Applies to form inputs where users must understand what information to enter. "Context-sensitive" means the help is relevant to the specific input — not just a generic "contact support" link. Mechanisms: inline description text (`aria-describedby`), placeholder text (supplemental, not sole source), a `?` help icon with tooltip, or a link to relevant documentation alongside the field.

## Common failure modes

- Complex form fields (e.g., date format "MM/DD/YYYY", phone format, password requirements) with no inline help text.
- Error messages that say "invalid input" without explaining the required format.
- Help available only through a general FAQ page, not linked from or proximate to the relevant field.
- `placeholder` text used as the only format hint — placeholder disappears on input and is not help in the WCAG sense.
- `aria-describedby` referencing an empty or irrelevant element.

## Attestation guidance

To attach evidence to an `attest` call (`ra11y-kb://criteria/wcag22/3.3.5`):

- Review every form field that requires specific formatting or domain knowledge.
- Confirm context-sensitive help exists: inline description, help icon + tooltip, format hint, or documentation link.
- Verify help is accessible to screen readers via `aria-describedby` or adjacent text.
- Verify help is visible (or discoverable) before the user makes an error — not only in the error state.

Evidence: annotated form screenshots showing help mechanisms, screen reader output confirming descriptions are announced.
