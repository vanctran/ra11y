# 3.1.4 Abbreviations

**Level:** AAA | **Standard:** WCAG 2.2
**Spec:** <https://www.w3.org/TR/WCAG22/#abbreviations>

## Why manual

Detecting abbreviations in running text and verifying that an expansion mechanism exists requires NLP-level text analysis. Static analysis can find `<abbr>` elements but cannot identify bare abbreviations (e.g., "API", "CSS", "VPN") in prose that lack any markup or expansion mechanism.

## What to verify

> "A mechanism for identifying the expanded form or meaning of abbreviations is available."

Applies to all abbreviations: acronyms ("WCAG"), initialisms ("HTML"), truncations ("etc.", "dept."), and contractions. Mechanisms include: `<abbr title="expanded form">`, first-use expansion in parentheses, linked glossary, or a pronunciation key.

## Common failure modes

- Bare acronyms throughout documentation (e.g., "Use the API to call the CMS via HTTPS") with no expansion mechanism.
- `<abbr>` elements used without a `title` attribute.
- Abbreviations defined once on a page but not expandable on subsequent pages that use them.
- Navigation and UI labels using abbreviations (e.g., "Mgr.", "Dept.", "Approx.") without expansion.
- Screen reader inconsistency: bare "CSS" may be read as "C-S-S" or "css" depending on AT settings — `<abbr title="Cascading Style Sheets">` ensures consistent expansion.

## Attestation guidance

To attach evidence to an `attest` call (`ra11y-kb://criteria/wcag22/3.1.4`):

- Scan content for abbreviations, acronyms, and initialisms not wrapped in `<abbr title>`.
- Confirm each has a first-use expansion, `<abbr title>`, or glossary link on every page where it appears.
- Verify `<abbr title>` values are non-empty and accurate.
- Test screen reader announcement of `<abbr>` elements to confirm expansion is read.

Evidence: list of abbreviations per page with expansion mechanism noted; screen reader output for key abbreviations.
