# `aria/hidden-focus`
- **Severity:** error
- **Scope:** node
- **Satisfies:** `wcag22:4.1.2`, `wcag21:4.1.2`
- **Applies to:** .html, .htm, .tsx, .jsx
## What it checks
Elements with aria-hidden="true" must not be focusable and must not contain focusable descendants. Keyboard focus and the accessibility tree must agree.
## Why it matters
aria-hidden="true" removes an element and all its descendants from the accessibility tree, but focus order is governed by the DOM and tabindex — not ARIA. If a focusable element is hidden from assistive tech, a keyboard user tabs to it and the screen reader says nothing. This is one of the most frequently-cited ARIA anti-patterns and a direct 4.1.2 failure because the focused component has no programmatically determinable name or role.
## Normative quote
> For all user interface components (including but not limited to: form elements, links and components generated by scripts), the name and role can be programmatically determined; states, properties, and values that can be set by the user can be programmatically set.
## Good example
```tsx
<span aria-hidden="true" tabindex="-1">Icon</span>
```
## Bad example
```tsx
<button aria-hidden="true">Close</button>
```
