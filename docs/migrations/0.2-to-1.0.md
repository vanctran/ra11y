# Migrating from ra11y 0.2 to 1.0

**TL;DR — v1.0 is additive for most consumers.**

- Rule IDs, coverage/checklist split, core package shape, and sampling-tool surface are all unchanged from v0.2. The four biggest speculative breaking changes were deferred past v1.0 (see ADR 0018).
- The only semver-major surface change is the **exit-code table**, which is now frozen. If you hardcoded exit-code integers rather than the documented values, verify your CI scripts.
- The `sessionConfigure` tool rename from `configure` becomes **permanent** at v1.0. The `configure` alias continues to work but emits a deprecation warning.
- The `filePath` parameter alias on `suggest_fix` and `apply_fix` continues to work but emits a deprecation warning.
- Plugin authors: the public API (`defineRule`, `defineStandard`, `defineFormatter`, `defineConfig`) is now frozen at v1.0. No shape migration is needed; no new required fields were added.

---

## What is NOT changing at v1.0 (deferred decisions)

These four items were open questions heading into v1.0. All four were closed as **deferred past v1.0** in [ADR 0018](../adr/0018-v1-deferred-decisions.md). They are listed here so consumers know not to expect them — and so a future minor can revive each on real evidence.

### Rule-catalog renames — not in v1.0

The overlapping families (`parsing/duplicate-id` + `parsing/html-has-lang` vs `document/lang-attribute`; `semantics/label-in-name` vs `forms/labels-required`) are unchanged. Every rule name from v0.1.0 and v0.2.0 is still valid. No migration needed.

Revisit signal: three or more user issues about name clarity after v1.0, or a new rule family that exposes unresolvable overlap. See ADR 0018 §1.

### Coverage + checklist split — not in v1.0

`coverage` and `checklist` remain separate tools. The ADR 0010 boundary is unchanged. Agents should continue calling them as a pair via `nextStep` / `nextStepStructured`. No merge, no verbosity knob.

Revisit signal: a concrete agent workflow where coverage-then-checklist round-trips dominate call budget. See ADR 0018 §2.

### `@ra11y/parser-typescript` subpackage — not in v1.0

TSX parsing stays in `@ra11y/core`. The optional `typescript` peer-dependency is unchanged. No subpackage to install.

Revisit signal: a production consumer reporting the optional peer still pulls the compiler against their will, or a second non-trivial parser candidate (Vue SFCs, Svelte). See ADR 0018 §3.

### Sampling-backed speculative tools — not in v1.0

`resolve-component`, `verdict-candidate`, and `draft-vpat-narrative` are not shipping. The existing `prompts/` + `attest` round-trip remains the recommended attestation path. `tools/list` is authoritative for what ships.

Revisit signal: a sampling-capable host surfaces a concrete workflow demand. See ADR 0018 §4.

## Breaking changes at v1.0

### Exit-code table is now frozen semver-major surface

**What changed.** `src/cli/exit-codes.ts` now exports the `ExitCode` enum as the canonical source of truth. Every CLI command returns exactly one of the four values below. The enum is frozen: any change to its values is a semver-major change.

| Code | Constant | Meaning |
|------|----------|---------|
| `0` | `ExitCode.OK` | Success; no action required |
| `1` | `ExitCode.VIOLATIONS` | Violations found, or command-specific failures (doctor probes, init refusal) |
| `2` | `ExitCode.USER_ERROR` | Invalid arguments, unknown rule, unknown profile, malformed input |
| `3` | `ExitCode.NEW_VIOLATIONS` | `--diff` / `scan_diff` mode only: new violations absent from the baseline |

**Why.** Scripts checking `$?` depend on stable codes across upgrades. Freezing at v1.0 makes exit-code semantics semver-major, so scripts can rely on the table without re-reading release notes.

**Who is affected.** CI scripts or agents that tested for a specific exit code on a path that previously returned a different value. In practice, exit codes 0, 1, and 2 behaved this way in v0.1.0/v0.2.0 as well. Exit code 3 was documented in v0.1.0 (`--baseline` mode) and v0.2.0 (`scan_diff` baseline mode). The freeze is a guarantee, not a change in observable behavior.

**Before (v0.2.0 — undocumented reliance on code 3 from a scan path):**

```bash
ra11y scan src/
if [ $? -eq 3 ]; then echo "new violations"; fi
```

If that scan path previously returned 0 or 1 when it should have returned 3, the freeze corrects it. Verify any CI branch on exit code 3 is actually reachable via `--diff` or `scan_diff` and not from a plain `scan`.

**After (v1.0):**

```bash
ra11y scan --diff src/
# $? is guaranteed to be one of 0, 1, 2, 3
# 3 is only reachable from --diff / scan_diff baseline mode
```

**Canonical references.** `docs/cli.md` — exit-code table. `docs/errors.md` — full error + exit-code reference. `src/cli/exit-codes.ts` — the enum itself.

## Stable-marked surfaces at v1.0

The following surfaces are frozen at v1.0. Changes to their shape are semver-major.

| Surface | Reference |
|---------|-----------|
| `ExitCode` enum values | `src/cli/exit-codes.ts`, `docs/cli.md` |
| `defineRule` / `defineStandard` / `defineFormatter` / `defineConfig` plugin API | `src/api/`, `docs/plugins/` |
| `Rule`, `Standard`, `Criterion`, `Config` TypeScript shapes | `src/types/` |
| MCP tool names on `tools/list` | `src/mcp/tools.ts` |
| MCP tool input/output shapes | `src/mcp/tools.ts`, `docs/mcp/` |
| Structured error codes | `docs/errors.md`, `src/mcp/tools-helpers.ts` |

These surfaces were present and tested in v0.2.0 and carry no shape changes at v1.0. The freeze is a guarantee going forward.

## Upgrade steps

### Most consumers: bump and run

If your agent calls `scan_project`, `checklist`, `coverage`, `suggest_fix`, or any other MCP tool, and you migrated to v0.2.0 shapes (see the [0.1-to-0.2 guide](./0.1-to-0.2.md)), there is nothing further to do. Bump to v1.0 and run your next scan.

### CI consumers: verify exit-code assumptions

1. Audit every `$?` check in your CI scripts against the four-row table above.
2. Confirm that any branch on exit code 3 is reachable only via `--diff` (CLI) or `scan_diff` (MCP baseline mode).
3. If you were relying on undocumented behavior where a plain `scan` returned code 3, migrate to `--diff` mode or remove the branch.

### Plugin authors: no shape migration needed

The plugin API shapes (`defineRule`, `defineStandard`, `defineFormatter`, `defineConfig`) are frozen as-is. No new required fields were added between v0.2.0 and v1.0. Verify by running `bun run verify` against your plugin; if it passes on v0.2.0, it passes on v1.0.

## Backwards-compatibility escape hatches

### `configure` → `sessionConfigure` alias

The `configure` MCP tool name was renamed to `sessionConfigure` in v0.2.0. In v1.0 the `configure` alias remains but emits a deprecation warning code:

```json
{ "warnings": ["deprecated_tool_name_configure"] }
```

Migrate when convenient by replacing `configure` with `sessionConfigure` in your tool calls. The parameters are identical.

### `filePath` → `file` alias on `suggest_fix` and `apply_fix`

The canonical parameter name for the target file on `suggest_fix` and `apply_fix` is `file`. `filePath` is accepted as an alias and emits:

```json
{ "warnings": ["deprecated_param_filePath: use 'file' instead"] }
```

Passing both `file` and `filePath` in the same call returns `conflicting-file-params` as a structured error. Drop `filePath` and use `file` only.

### `coverage`: `showUntargeted` to restore the full untargeted list

Since v0.2.0, `coverage` omits the full `untargetedCriteriaList` by default. The count `untargetedCriteria` is always present. Pass `showUntargeted: true` if you need the per-criterion list:

```json
{ "tool": "coverage", "params": { "showUntargeted": true } }
```

This behavior is unchanged at v1.0; it is listed here for consumers who skipped the 0.1-to-0.2 guide.

## Appendix: new surfaces at v1.0 (not breaking, but worth noting)

These are additive changes between v0.2.0 and v1.0 that consumers may want to opt into:

- **`audit` meta-tool** — one-call `scan` + `coverage` + `checklist` for cold-start onboarding.
- **`bootstrap` meta-tool** — single-call onboarding composing detection, config proposal, scan, and optional baseline creation.
- **`apply_fix` tool** — write-gated fix loop (requires `allowWrite: true` in session config).
- **`scan_diff` tool** — per-scan baseline delta; returns only new violations since a baseline snapshot.
- **`baseline` tool** — create/check/update baseline within an MCP session.
- **Prompt templates** — `ra11y/triage`, `ra11y/fix`, `ra11y/audit`, `ra11y/vpat-narrative` served via `prompts/list` and `prompts/get`. Referenced in `nextStep` guidance on scan responses. See `docs/mcp/prompts.md`.
- **Structured error codes** — all tools now return `structuredContent` with a `code` field on error. See `docs/errors.md`.
- **Inline disable reason annotation** — `ra11y-disable wcag22:1.4.5 -- confirmed logotype` captures the reason in `meta.suppressions`.
- **Coverage matrix** — `docs/kb/standards/coverage.md` publishes the per-criterion automatability classification; CI drift check keeps it current.
- **`preset: "storybook"` config option** — opt-in preset that includes story files in the scan and marks Storybook primitives as transparent wrappers.
- **`afterProject` finder hook** — finders implementing `afterProject` can emit cross-file review candidates (used by `consistent-navigation`, `consistent-identification`, and page-set finders).
- **Inherited findings** — `Violation.confidence === "inherited"` + `Violation.sourceOfFinding` propagates wrapper-definition findings to call sites.
